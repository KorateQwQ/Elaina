# 净土露滴：三格净化与彩虹 Shader

正式逻辑位于 `ElainaModAlchemy/Purification`，物品为 `item/Potions/PurificationDew.cs`。正式材质是 `Effects/Content/PurificationDew.fx` 和编译后的同名 XNB。无需新增材料、图标或轮廓资源。

## 行为与同步

- 使用距离 60 格；目标对齐格中心。以 8 像素/tick 向世界底部移动，每次处理目标列及左右各一列，共 3 格。穿过实心物块和液体，最后一行是世界边界内侧。无伤害，不剪草，不修改背景墙。
- 单机直接创建；联机拥有者先发送手持槽同步和带序号的目标请求，再由原版消费一件。服务器校验发送者、距离、物品、冷却和弹幕池空槽，生成服务器拥有的弹幕。请求被拒后只向原拥有者确认，拥有者退回一件；重复确认不会重复返还。库存仍遵循 Terraria 的客户端拥有模式，不是反作弊的服务器库存系统。
- 不限制每人或全世界同时存在的露滴数量；保留正常 30 tick 使用间隔，满弹幕池拒绝使用，不替换其他弹幕。每个露滴每 tick 最多处理一行、三次单格转换，总工作量随数量增加，普通速度下每两 tick 推进一行。`WorldGen.Convert(..., size: 0, tiles: true, walls: false)` 复用原版及模组转换入口和地形同步；探图另向使用者补充下面说明的窄条地形。
- 客户端露滴只表现，禁止执行净化；服务器拒绝客户端拥有的伪造露滴。ai 同步起始行、年龄、使用者；位置每秒校正，`netImportant` 支持中途加入。已经过的坐标永久受到保护。不持久保存正在下落的露滴，退出世界会终止它，但已形成的净土随世界保存。

## 永久净土（2026-10-25）

`PurificationProtectionSystem` 在净化前登记该行三格坐标（包括空格），按列合并相邻或重叠的 Y 区间。保护绑定位置，挖除后重新放置仍然有效；中途退出只保存实际经过的范围，不把未经过的下方提前保护。`PurifiedColumnsV1` 写入模组世界数据；老存档缺少此键时按空记录读取，无法还原旧版露滴的使用历史，需要重新使用。

拦截点均为原版事件，没有每帧/定期扫描整条隔离带：

- `TileLoader.Convert`：目标在净土内时拒绝 Corruption / Crimson / Hallow。覆盖常规感染、粉末/溶液和困难模式 `GERunner`；纯净转换及其他非感染转换仍可执行。
- `WorldGen.SpreadGrass`：阻止感染草种进入净土，保留普通草生长。
- `WorldGen.GrowMoreVines`：感染源下方为净土时不允许长藤蔓；普通藤蔓仍可生长。
- `WorldGen.TileFrame`：在原版荆棘刚激活、尚未完成本次更新和发包时清除它；同时处理藤蔓按上方草种改色、感染块重新放置、落沙落地和原版收到 TileSquare 后的 RangeFrame。先按物块类型快速排除普通物块，只有感染块查询保护区间；递归净化有线程局部重入保护。

露滴经过时额外清除原版 Purity 未处理的感染藤蔓/植物。只清除目标格，不通过 KillTile 连带清除区域外整条藤蔓。保护和清理均保留背景墙、液体、电线；背景墙的感染状态不属于本功能，未阻止墙自身的传播。原版这些墙不会因此跨过净土把另一侧物块染色。隔离效果要求保护区域连续，不能阻止传播绕过未封闭的端点；困难模式仍可在区域外直接生成新的感染带。

联机由服务器登记与修复地形，客户端同步保护坐标以阻止本地溶液预测染色。露滴每 8 行随既有批次广播一个小型增量，结束补发尾批；与只发给使用者的探图消息分开。玩家进入世界时请求完整快照，每包最多 256 个区间；无需下载整个世界区块，也不在每次 WorldData 中重复传输保护列表。服务端拒绝客户端提交保护增量。区间查询和变更加锁，兼容困难模式生成线程。

`checks.ps1` 当前通过 56 项原有净化检查、24 项地图检查及 111 项永久保护检查。后者使用真实安装的 tML 引擎，覆盖七类物块的三种转换、普通/感染草、藤蔓生长与原版改色、两种荆棘各 400 次实际 GrowSpike、八种感染源各 1500 次 hardUpdateWorld、四组真实 GERunner、挖除重放、RangeFrame 修复、保留墙液体电线、压缩 TagIO 存取、旧存档、客户端预测、两包中途加入快照、增量同步与拒绝客户端伪造。网络发送被捕获，没有真实多人服务器连接。

可复现查询测量保存于 `benchmarks/2026-10-25/permanent-protection.json`，重跑输出 `.vissandbox/purification-dew/benchmark-protection.json`。1 / 64 / 256 条、每条 2200 行的连续隔离带下，10 万次混合命中/未命中查询中位数分别为 1.627 / 1.639 / 1.635 ms；仅测区间查询及循环调用，不代表整个游戏帧时间。每条连续隔离带只保存 9 个 int（36 字节的原始区间值），256 条为 9216 字节，不含字典、列表、NBT 格式等额外开销。

已检查本轮中英文手记的 FNA 离线截图，覆盖默认和 125% 缩放；完整模组编译、正式轮廓检查、翻译键检查及独立打包通过。尚未在正在运行的游戏或真实多人服务器中复验。只保证本轮检查覆盖的原版路径，其他模组绕过转换、更新和 framing 直接修改物块仍需单独兼容。

## 沿途探图（2026-10-25）

`PurificationDewMapSystem` 在露滴实际净化一行后，为使用者揭开该行左右各 4 格、共 9 格的地图。中央三格亮度 255，外侧为 210 / 165 / 120；保留已有更亮的地图。探图独立于屏幕光照范围，原来的 AddLight 继续提供现场照明。地图沿用原版世界边缘 40 格黑边；净化仍然只有三格宽。

单机每经过一行入队一次；联机服务器每 8 行向使用者发送一条最多 9×8 的原版 TileSquare，随后按同一连接发送开图通知，结束时补发不足 8 行的尾批。这样即使远处区块尚未下载，也能按真实地形开图，不需要请求整个 200×150 区块；不向其他玩家广播探图，不由客户端预测位置补扫历史行。每道露滴常态每秒约 270 格，约 3.75 批（每批地形和通知各一包）；没有实测网络带宽。

客户端通过 WorldMap.UpdateLighting 写地图，并加入原版 MapHelper 的逐格刷新队列。所有露滴合计每 tick 最多处理 32 行 / 288 格；队列不足时保留到后续帧，不设置 refreshMap，不扩大全图扫描范围。相同地图数据不会重复提交刷新，加载地图时暂停处理，退出世界清空待处理行。此预算只调度地图工作，不限制露滴的释放数量或净化速度。

`checks.ps1` 编译完整模组，执行原有 56 项检查及新增 24 项真实地图引擎/捕获传输检查，覆盖屏幕外地图类型、渐暗范围、保留亮度、世界黑边、刷新队列满后重试、逐帧预算、世界清理、联机批次/接收目标/包顺序、结束尾批和异常请求。联网部分捕获实际发送入口与 ModPacket 字节，没有真实套接字连接；尚未在运行中的游戏或真实多人环境复验。

地图 CPU 测量保存在 `benchmarks/2026-10-25/map-exploration.json`，重跑输出 `.vissandbox/purification-dew/benchmark-map.json`。每道处理一个新行，计时包含真实 WorldMap / MapHelper 更新及脏格入队，清图和待处理行入队在计时外。300 个有效样本：1 道中位数 0.0006 ms，8 道 0.0058 ms，32 道 0.0201 ms；64 道按预算分两次处理，合计 0.0391 ms。此数字不含 GPU 地图绘制、地形包编解码、网络传输或其他模组地图钩子开销，不能当作完整游戏帧耗时。

## 绘制契约

`DewLight/RainbowFall` 是 SpriteBatch 像素 Shader（ps_3_0）。s0 直接使用现有 KL 资源 `Effects/Tex/Trail/LightTrail2.png`（256×128，与用户提供贴图逐像素一致）；使用 LinearClamp。Effect 和拖尾贴图均借用 ModContent 资源，不克隆、不创建白纹理，不自行 Dispose。

视觉包围盒由旧版 48×240 收细为 24×210 像素；实际拖尾采用非线性渐缩宽度，前端较宽、尾端收尖。沿贴图长度从亮端到淡端采样，复用边缘纹理而非原先的等宽程序化光丝。`Time` 为年龄/60 秒，`Opacity` 负责渐入；保留小型前端彩虹光环、白亮露滴，色相沿尾迹缓慢流动。

输出为 HDR 发光 RGB、alpha=0，以 AlphaBlend 叠加而不遮暗场景。通过 `DrawBehind` 提交到魔力飞弹同一 `LayerDrawRequestSystem.RequestBloom(Projectiles, After)` 队列；同层露滴、飞弹共享一次亮部提取、下采样、上采样与合成。关闭 KL Bloom 时仍绘制原始窄拖尾。没有为每个露滴分配全屏目标。旧版“没有全屏后处理”和旧性能数字不适用于此版：现在会使用 KL 已有的共享 Bloom 后处理。

Renderer 只借用正式 Effect 和拖尾纹理，没有自建 GPU 资源。提交前进行屏幕范围检查；弹幕 Bloom 回调末尾直接调用 KL `DrawHelper.EndBeginDraw()`，不反射读取 SpriteBatch，也不实现任意绘制状态的保存/恢复。专用服务器不创建图形资源。材质无法加载时退回物品贴图。

## 旧版多道露滴的独立性能测量（2026-10-25，接入共享 Bloom 之前）

运行 `run.ps1 -Benchmark` 测绘制，`checks.ps1 -Benchmark` 测真实引擎转换。最终两项分开运行，避免编译/另一项测试同时占用资源。原始数据在 `benchmarks/2026-10-25/`，含样本数和 P95。

本机 Ryzen 9 9950X3D；FNA3D 日志报告 RTX 5080 / D3D11（GraphicsAdapter.Description 返回的是显示器 XG27UCS）。1920×1080、100% 缩放、所有尾迹完整在屏幕内；每道 48×240 像素。绘制值包含 CPU 提交、GPU 完成和一像素读回，表中为各场景中位数减空场景中位数 0.3421 ms 的估计增量，不是纯 GPU 时间或游戏帧时间。

| 同时数量 | 绘制估计增量 | 所有露滴同 tick 净化一行的 CPU 中位数 | 连续感染石块下每秒地形更新调用数 |
| --- | --- | --- | --- |
| 8 | 0.048 ms | 0.029 ms | 720 |
| 16 | 0.059 ms | 0.058 ms | 1440 |
| 32 | 0.089 ms | 0.121 ms | 2880 |

转换测试预热真实 WorldGen 和 framing 后计时，每道处理三个腐化石块；重置图块在计时外。NetMessage.SendData 被捕获计数，不包含封包序列化、网络发送、多客户端处理和其他模组的转换钩子。每秒更新数按 60 tick/s、8 px/tick、三格宽的稳定下降速度计算；已经纯净的石块不发送地形变化。这里没有测量带宽，也没有验证几十道同时工作的真实联机体验。

结果不支持“超过八道就会卡”，更不支持把每人一道解释为测得的性能阈值。初版数量限制是保守实现选择。现已按用户要求移除每人一道及全服八道的数量限制，不新增全局调度限额，由玩家自行决定同时释放数量。

解除数量限制后的回归检查覆盖：同一玩家在正常使用间隔后继续释放、第九道正常生成、累计 32 道不阻挡后续使用。保留重复请求幂等、失败返还、客户端禁写及满弹幕池保护。原性能测量仍适用于相同的绘制与逐格净化实现。

## C# 热重载调参与简化绘制

常用数值集中在 `ElainaModAlchemy/Purification/PurificationDewVisualSettings.cs` 的 `Read()` 方法体：`SwaySpeed`、`SwayAmplitude`、`ColorSpeed`、`Width/Height`、`TaperExponent`、拖尾/头部/光环亮度等。每帧重新读取并上传 Shader 参数。不要将这些值改为只在初始化时赋值的静态字段。

这次新增 Shader 参数与纹理槽调整必须先完整构建并加载一次；之后使用支持 C# Hot Reload 的调试会话修改 Read() 方法里的数字即可，无需再次编译 FX。改变 Shader 运算本身、贴图文件或参数接口仍需要相应资源构建/加载。保存 C# 文件本身不等于已经应用热重载。

`pwsh -File Tools/PurificationDewPreview/hotreload.ps1` 使用独立临时源码副本和隐藏 FNA 窗口，通过真实 `dotnet watch` 验证五项方法体数值变更。修改前后进程 ID 一致，原有资源 Effect 的 uniforms 收到新值。该检查不操作用户的游戏进程。生产代码无反射、Effect.Clone、new Texture2D 或 Dispose；离线预览工具自己拥有的窗口/纹理等资源仍正常释放。
